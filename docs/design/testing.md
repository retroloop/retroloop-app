# Testing

**Philosophy: "Test, not debug."** Behavior is proved with reproducible tests. Nobody drives a browser by hand, pokes state files, or fixes anything without a red test first.

## Running the suites

```sh
bun install
bun run test    # scripts' own tests + every workspace suite (core, api, cli, web)
bun run e2e     # the all-real end-to-end suite
bun run gate    # everything, in the order that fails cheapest first
```

`bun run gate` (`scripts/gate.sh`) is the merge bar: a change is done only when it exits 0. It runs, in order:

1. `bun install --frozen-lockfile` — reconciles install state with `bun.lock`. It heals the lag a `worktree add`, `merge` or `rebase` leaves behind, and refuses a real dependency change, which is a decision somebody has to make rather than a state the gate may repair.
2. `tsc --noEmit` per package, then for the scripts and `e2e/` root.
3. `biome ci .` — lint and format.
4. The enforcement scripts: dependency direction, mock lock, mock parity.
5. `bun test scripts` — the enforcement scripts' own tests. A gate that cannot fail is no gate.
6. `bun test` in `packages/core`, `apps/api`, `apps/cli`.
7. The `apps/web` Gherkin suite over headless Chromium, including the zero-console-error check.
8. The all-real `e2e` suite.

A single suite is run directly where the work is: `cd apps/web && bun run test` regenerates the BDD glue and drives Chromium; `bun run --filter '@retro/core' test` runs one package.

## The core concept

**Every layer boundary is a typed contract. Test each layer against the contract below it, with the layer below replaced by a fake implementing the same imported type. Prove each real dependency's behavior once, in isolation. A handful of all-real scenarios prove only the wiring.**

- **Shape is locked by the compiler:** fakes implement types imported from the producer (`AppRouter`, `RecordRepository`). Producer changes → fakes and their tests fail to compile. Suites can't drift because they share a *type*, not code.
- **Behavior is locked by integration tests, once:** types don't say "a miss returns `undefined`" or "`BEGIN IMMEDIATE` serializes writers" — the real dependency is proven through its interface; after that every consumer may trust an honest fake.
- **Wiring is what's left:** composition roots, config, embedded assets, tailer→SSE. That's what the few all-real e2e scenarios exist for — few, because everything else is already proven cheaper one layer down.

## Layer / suite matrix

| # | Suite | **Tests** | **Real** | **Faked** | **Absent** |
|---|---|---|---|---|---|
| 1 | Dependency integration | L1 (both adapters) + migrations | L0 SQLite temp file, L1 sqlite | memory adapter runs the same contract suite as reference | L3+ |
| 2 | Application via tRPC (`createCaller`) | L4a routers, context, error map, subscription replay | L2, L3, L4a | L1 memory, Clock, IdGen | L0 HTTP, L5, L6 |
| 3 | CLI → Application (yargs in-process) | L4b args → `--json` shapes, exit codes | L4b, L3 | L1 memory, Clock, IdGen | L4a, L5, L6 |
| 4 | Web Gherkin over mocked tRPC (playwright-bdd, headless Chromium) | L5 | L5, L6 | L4a via the typed mock; subscription mock feeds `useLiveSession` | L0–L3 |
| 5 | Core E2E Gherkin, all real | the whole loop | binary CLI, server, two browser contexts, export file | nothing | L7 service registration |
| 6 | Static | source of all layers | `tsc --noEmit`, Biome, dependency-direction + mock-lock scripts | — | — |

**Always-on (the merge gate):** suites 1–6. Size caps: one contract suite per repository, plus read-model contract suites for use cases whose semantics must hold on both stores (first: `list-retros.contract.ts`, N4); one test per procedure happy-path + each typed error; one test per CLI command; every UI behavior in suite 4; **suite 5 capped at ~3 scenarios** (full loop · real-time two pages + CLI write · upgrade old DB → new binary). Runtime targets: 1–3+6 well under a minute; 4 in ~1–2 min; 5 in ~2 min; whole gate < 5 min. `retries: 0` — a flaky test is a bug in the test.

**On-demand only** (written when a ticket needs them): pure use-case unit tests; cross-process concurrency; WebKit runs (iPad parity — nightly or on report); visual regression `toHaveScreenshot`; install matrix on Windows/Linux (release tags); performance/large-ledger.

## R-MOCK-LOCK

> **R-MOCK-LOCK.** In `apps/web`, tRPC is mocked **only** by an implementation typed from `AppRouter` imported from `@retro/api`. There is exactly one mock module: `apps/web/test/trpc-mock.ts`. It must cover every procedure of the real router — no more, no fewer — with inputs/outputs typed as `inferRouterInputs<AppRouter>` / `inferRouterOutputs<AppRouter>`. No file under `apps/web` may define routes, handlers, fetch interceptors, response literals, or a second router. A PR that violates this is rejected regardless of whether tests pass.

The rule rests on a simpler one — the typecheck is the lie-check — and strengthens it, because knowing the principle has not been enough to stop a custom router being slipped into the UI.

**Widening any tRPC output is necessarily a two-package change:** every wire shape is a `z.strictObject` and the mock is `satisfies MockRouter`, so a new output field fails the web typecheck and the parity gate until the mock models it. "Additive only, don't touch `apps/web`" is an impossible pair — a wire widening belongs to the same change that owns the typed mock, never split from it.

**Four ways the mock can lie, and who catches each:** a **missing** procedure, an **extra** procedure and a **mis-shaped** procedure are the compiler's, below; an **extra field canned into a procedure's answer** is not, and never was — TypeScript infers an arrow handler's return type from its literal and then checks the whole function type for assignability, so excess-property checking never fires on the answer. That fourth direction belonged to human review alone — the most expensive detector the repo runs — until `scripts/check-mock-parity.ts` took it.

**Enforcement, three layers:**
1. **Compiler:** the mock is `satisfies MockRouter` (mapped type over the real router's procedure keys — missing, extra, or mis-shaped **procedures** fail to compile, and a field whose *type* is wrong fails with them); `web → api` is type-only (`verbatimModuleSyntax`, `useImportType`; `initTRPC`/router values unimportable).
2. **Gate scripts:** Biome `noRestrictedImports` bans `@trpc/server`, `initTRPC`, `msw`, `nock`, `node:http` in `apps/web`; `scripts/check-mock-lock.ts` fails on any second mock/link/handler definition; a procedure-set meta-test in `apps/api` asserts the mock's keys equal the real router's; and `scripts/check-mock-parity.ts` runs every mock procedure against the mock's own fixture world and validates each answer with the schema the real router validates it with — every shape in `views.schema.ts` is a `z.strictObject`, so an extra canned field fails the gate at any depth, including inside a list row and inside a streamed event's payload.
3. **Review:** every change touching `apps/web/**`, `apps/api/src/trpc/**`, or `e2e/**` is reviewed against a binary checklist, with file:line evidence for any failure. Exactly one mock module? Typed from `AppRouter`? Any value import from api in web? Any handler/fetch/route in web? Any response literal not derived from `inferRouterOutputs`? Any `.feature` step bypassing the tRPC client? **Plus the UI-minimalism check: what did this change add to the UI, and which requirement paid for it?**

**The pinned lists are FOUR, and adding a procedure or a use case moves all of them.** The count is what a change budgets by, so an enumeration that undercounts reads as complete while leaving a red test — which is exactly what happened when a change added a use case and met a fourth list nothing had named:

1. **`apps/api/test/procedures.test.ts`** — the real router's procedure set, asserted as a named list rather than a count, so a newcomer fails by its own name. Two removed groups (`requests.*`, `holds.*`) are asserted here by absence, and a procedure that came back would fail here too.
2. **`apps/web/test/procedure-set.spec.ts`** — the same set from the typed mock's side, computed from `AppRouter` as `ProcedurePath`. Between the two, the mock cannot quietly drift from the thing it stands in for.
3. **the `PLAN` in `scripts/check-mock-parity.ts`** — the list that has to actually *call* a procedure before any answer of it can be validated, and the one that gets forgotten because presence failures are the other two's job.
4. **`packages/core/test/unit/app.test.ts`** — the App's whole use-case set, sorted and named. It fires on **use cases**, procedure-backed or not, so core work with no wire surface still trips it; it is the list the api/web/parity vantage cannot see, and it has failed exactly as designed.

**A plan step that reads a shape another step populates runs after that step.** The fixture world accumulates across the plan, so a listing taken before any mutation validates only the empty half of a null-until-populated shape, and an extra field canned into the populated half sails through. Proven in both directions with a planted field on `recordLifecycleSchema`: caught with the lifecycle write ordered first, silent with the listing first.

## Determinism

- **Fake `Clock` and `IdGen` ports** everywhere below e2e; `RETRO_TEST_CLOCK` env for spawned processes; seeded fixtures; serial Playwright projects for real-time scenarios and for the starvation class (`apps/web` §the `starved` project, and the stall-edge passage below for when a scenario belongs in it); temp root (`--home`) + random port per run; `data-testid`-only selection in web tests.

## Operational rules

- **A bug is a failing scenario first,** at the lowest layer that can express it. The fix is done when that test passes and the rest stay green.
- **A race or flake investigation opens with instrumentation, never with a fix.** The first act is a trace that reproduces the mechanism, and the evidence for the fix shows the trace that convicts it. A diagnosis handed down by someone who did not instrument is a hypothesis, and both of the hypotheses below were wrong: "the page grows after the click" died on 25 traces whose `scrollHeight` never moved (the real cause was an unsettled smooth scroll racing the assertion band), and a focus-handoff theory died when the failure hit with focus already polled onto the tab (a single non-retrying `evaluateAll` racing React's commit; the right tab reads correct 5ms later). Either fix would have changed the wrong thing and left the flake alive under a claim of victory.
- **A settled-wait and the reading taken off it stay two separate calls.** Folding the reading into the same `page.evaluate` as the wait is better engineering — the page cannot move between the rest and the reading — and it silently disarms the scenario that certifies the wait. `expect.poll` accepts one long call however late it returns; its budget only bites *between* iterations, so a wait that concludes far too late stops being a failure and becomes a slow pass. Measured rather than reasoned: with the fold applied, the pre-fix wait the starved-renderer scenario exists to catch passed **10/10**. So in `apps/web/features/steps/review.steps.ts` the `scrollAtRest(page)` call and the landing read that follows it sit inside the poll as two calls on purpose — a lock the poll can interrupt, not a refactor waiting to happen. **The two are mutually exclusive and the lock wins**; this is words only, deliberately, because the code is already right and what was missing is the reason at the place it constrains.
- **A measurement travels with its parallelism, or it is not reusable by anyone including its own author.** Every rate or flake number states its **worker count and repeat form**; **"in isolation" MEANS `--workers=1`** and may not be claimed otherwise; **`--repeat-each N` under `fullyParallel` is N concurrent copies** — a load test, not a repetition, so a soak supplies its own contention; and two measurements are comparable only when their stated methods are. One flaky scenario was characterized five times in one night, each superseding the last — load-dependent, then ~40% "in isolation", then identical on both shells, then not this change's — and settled only at the end: 6/6 green at `--workers=1` and red only under parallel runs, on every branch including main, the serialized run spending **12.4s of the starved renderer's 15s budget**. Every earlier "isolated" number had measured a different condition under the same word. Instrumentation was never what failed; what no rule governed was the VOCABULARY a number travels in.
- **A verdict travels with the machine it was taken on.** Every gate or suite result is recorded with **loadavg and swap at its moment** — the rule above widens from the run's own workers to the box they ran on, because a starved renderer burns no CPU and a machine can be busy in a way the run itself cannot see. "Quiet" is a claim about the machine, and it cannot be manufactured by agreement: with nothing else of this project running, a gate still produced **four** timeout-shaped reds with browser-death signatures, under its own five-worker Chromium fleet at loadavg 42 on a box already holding swap at 11.1 of 12.3 GB under ~20 long-lived sessions from other work and 8 days of uptime — none of which any agreement about this project's own runs can reach. **And a substrate claim states its moment of measurement:** a swap reading of 0.00M taken at boot is not evidence that "the starvation substrate is gone" when swap reads 462M minutes later — true when it was read, false when it was quoted, which is the entire content of the rule.
- **The stall edge is a scheduling boundary, not a budget, and it has its own Playwright project.** This class was fixed at four layers over time — an unsettled wait, a re-scoped wait, a stall convicted under load, budget moves — and each fix was true where it stood. The shared trigger underneath all of them is **parallel contention against a wall-clock budget**: the landing scenario reads 6/6 green at `--workers=1`, spending 12.4s of its 15s budget, and red only under the suite's own parallel workers, identically on every branch. Re-measured before anything moved: green at the gate's five workers (16.6s), and **12 of 12 red at twelve concurrent copies on twelve workers** — every one of them `Timeout 15000ms exceeded while waiting on the predicate`, the page alive in all twelve, at loadavg 103. A bigger number cannot fix that, because the number a starved renderer competes with is *however many browsers the suite happens to be running*. So the class leaves the parallel bulk instead: `apps/web/playwright.config.ts` carries a `starved` project selected by a `@starved` tag (`grep` against the bulk's `grepInvert`), and **it takes both halves** — `workers: 1` alone caps only that project's own concurrency while Playwright fills the remaining slots with the bulk's browsers, so `dependencies: ['chromium']` is what makes it *afterwards*. The same boundary `e2e/playwright.config.ts` has always drawn, for the same reason. Debug one without the other with `--project=starved --no-deps`.
- **When a scenario belongs in the serialized project**, all three hold, and the tag is the whole of the membership: it **starves its own renderer on purpose** — holds the main thread, throttles the CPU, makes frames seconds apart — rather than being slow, being flaky, or having died once under load; its claim is then **read against a wall-clock budget** that the starvation is meant to outlast, so the budget is the thing contention spends; and the class stays **small enough to serialize**, which today is two scenarios and by its own cost argument is never many more. **The counter-criterion matters as much:** a red whose signature is a *browser death* — `Target page, context or browser has been closed`, `Protocol error … session closed`, a locator answering `undefined` — is not in this class however timeout-shaped it looks. That is the machine killing a browser under memory pressure, not a renderer overrunning a budget, and three candidates that carried exactly those signatures — the dashboard pending-count, records resolve-panel and portrait-iPad comment scenarios — deliberately did **not** move. Serializing such a failure would treat a memory casualty as a scheduling problem, and a criterion loose enough to admit them admits the whole suite.
- **What the boundary does not buy.** A dependency project that fails takes its dependents with it as skips, so under a red bulk the serialized project reports that it did not run — which is not a pass and must never be counted as one. And serializing removes the contention this suite creates, not the contention the box is under: the machine rule above still applies, unchanged.
- **A wait against a starved renderer is certified by its budget, and the harness cannot certify more than that.** Two limits are worth knowing before writing another scenario in this class. Playwright's `click()` does not return until the page has reacted to it, so a defect that lets a step return early is invisible: with the app menu's close-wait deleted outright the close was over at t=2040ms and the first reading that could be taken landed at t=2181ms, and the scenario stayed green. And the two starvation engines are not interchangeable — holding the page's main thread *quantises* it into whole periods and lets a close commit entirely inside one, between two of the harness's acts, so budgets are never spent and a plant against them is inert; Chromium's CPU throttle scales the work instead, so budgets are spent and a budget sized for a healthy page is red. The certification that survives both is the honest one: `chrome.feature` §the app menu opens, closes and arrives drives the whole menu walk at ×50 and is red with every budget in it cut to 300ms — 10 green → 10 red → 10 green, one worker.
- **A gate red is waivable only when ALL five of these hold.** The waiver covers exactly one thing — a red that belongs to the machine rather than to the change — and "timeout-shaped" was never sufficient on its own:
  1. **The red is the machine's, evidenced at its own moment** — a browser-death signature (`Target page, context or browser has been closed`, `Protocol error … session closed`, a locator answering `undefined`), recorded together with the loadavg and swap that produced it.
  2. **It is not in the serialized project.** A red there ran on one worker after every other test in the suite had finished, with nothing of this suite beside it — there is no contention left to attribute it to, so it is a failure and it blocks. The same holds when that project reports that it *did not run*: a dependency failure skips it, and a skip is not a pass. A starvation-shaped red in the parallel bulk means a scenario has joined the serialized class without carrying the tag, and the answer to that is the tag, not a waiver.
  3. **The diff is argued, and where possible verified, reader-free of the failing surface.**
  4. **One serialized whole-suite run is green.**
  5. **Both runs are pasted with their worker counts** — under the vocabulary rule above, "serialized" MEANS `--workers=1` — **and no retry is silent:** every re-run is stated, with what changed between them.

  Anything short of all five is a red that blocks, and the standard is applied by whoever accepts the change, never claimed by its author. **The counter-example is the standard's own proof:** a 0-second typecheck failure (`Cannot find module 'recharts'` — install-state lag, now healed by the gate's `bun install --frozen-lockfile` step) also produces a gate red, and the standard **refuses** to waive it, because a 0-second FAIL is nothing's contention and no serialized green can make it one. That refusal is what distinguishes a standard from an excuse. What stays waivable is a machine fact that no working agreement can reach; the occasions for it end when the box stops swapping.
- **Every NEW browser scenario is soaked before it merges:** run the new scenarios at `--repeat-each` of at least 10, and record the count and the result beside the change. One green run is a low bar and a 1-in-7 race passes it about 86% of the time, so two races once shipped inside a single merge and billed every session after it: multi-run gates, false suspicion of innocent changes, and `retries: 0` — a principle a reader can see — turned into a coin flip. Both fixes were trivial once diagnosed; the whole cost was in the escape. Scoped to new scenarios because soaking the suite on every merge is unaffordable and the marginal risk lives in what has never been repeat-run.
- **Plant-and-catch is a standing rule:** plant representative defects and watch your own suites catch them before claiming anything; say which plants were laid and what caught each. A check never observed failing is an unverified claim — this practice has found two real bugs that every written test passed.
  **Plant through `scripts/plant.sh`, which is the safe order rather than a reminder of it:** `scripts/plant.sh --check <check-cmd> [--expect-green] <file>… -- <apply-cmd>` refuses to run while any of its targets carries uncommitted work, and `scripts/plant.sh --revert` reverse-applies exactly the diff it planted — never a checkout, tree-wide or per-file, so work written into the file after the plant is not the plant and does not go with it. If the plant's own lines were edited under it the revert fails loudly and changes nothing, rather than guessing which half to keep.
  **The cycle is enforced, not described: green baseline → plant → red → revert → green.** `--check <check-cmd>` names the command whose red certifies the plant, deliberately separate from the apply command that lays it, and the harness runs it three times — before the plant, which must be **green** or there is no baseline a catch could be attributed to; with the plant applied, which must be **red** or the plant is inert and is rolled back rather than certified; and after `--revert`, which must be green again or the cycle certifies nothing. `--expect-green` is the single exception, for an absence assertion that legitimately stays green, and it is logged as an acknowledgement rather than as a catch. The failure this prevents is a plant that edits a tally but not the `useMemo` dependencies that recompute it: the diff is non-empty, the suite stays green, and the honest reading is "inert plant", not "the scenario failed to catch it". A non-empty diff was never evidence of anything. **All three results are logged as generated fact**, refusals included, in `$(git rev-parse --absolute-git-dir)/retro-plant.log`; read it with `scripts/plant.sh --log`. A plant table quoted anywhere is copied from that log rather than recollected, and the check's own full untruncated summary lines travel beside it.
  **A number quoted as a reading is PASTED from that log, never typed.** A certified cycle and a finished control END by printing that run's log block already formatted to paste — the green/red/green verdicts with the log's path above them — so the honest form is what the terminal already holds and inventing one costs *more* effort than copying it, which is where keystroke-level rules win and warnings lose. Any reading quoted anywhere a reader will trust it — a report, a test comment, a docstring — cites the path of the log that produced it, beside it; a reading with no citable log is written as **expected**, never as observed. The tool moved rather than the prose because a doc comment once asserted a control run that never happened, with invented numbers — "16 against a menu bottom of 56" where the real cycle read **18 against 57** — wrong on both figures and by too little to look wrong, and the author had this very rule in hand when writing it. Invented evidence does not look invented, and a number reads as measured *by being* a number.
  **Reverting a plant must never be able to take the fix with it.** A finished fix, its scenario and a fixture change — all uncommitted — are erased by a tree-wide `git checkout -- .` aimed at the plant, and all three have to be rewritten. It has happened in both forms: that tree-wide revert, and a single `git checkout -- <file>` run before committing a batch of finished fixes, which erased every one of them — by an author who had quoted this very rule in an earlier report. That is the shape of the failure: a habit asked for at the one moment attention is on the plant table rather than on git state, which is why the rule is a script. The order it enforces is the order that was always right, and the only part still left to a person is the first step: **commit the fix**, then plant, and the harness runs the cycle above.
  **A control is declared, never improvised.** Reproducing something against another tree's content — `git checkout main -- apps/web`, restored one command later — is byte-identical in git signature to the work-destroying revert above, and one has been read that way in practice: a read-only reviewer caught a legitimate control mid-run, and the cost was an emergency interruption and a complete re-take of that run's evidence. Intent cannot be observed, so it is declared: `scripts/plant.sh control --why "<what you are reproducing>" [--from <rev>] <file>… -- <cmd>` refuses a dirty target set on the same standard as a plant, snapshots the current files, writes the other tree's content **without ever touching the index** — `git show`, never `git checkout`, so the staged wholesale revert is a signature the mode cannot produce — runs the command, and restores the tree unconditionally, on success, on failure and on interrupt. The declaration is written to the log **before the command starts**, because an observer who can only read it afterwards is reading an explanation rather than a declaration. Two habits ride along as the rule the mode implements: **never revert your own files for evidence** — a control borrows content, it does not undo work — and **print `git status --porcelain` beside every number**, so the tree state is on the record next to the result it produced.
  **After ANY content restore — plant revert, control, checkout — rebuild before serving, and verify the bundle carries your change.** A restore puts *source* back and rebuilds nothing, so `apps/web/dist` goes on serving the bundle built before it. This is the mirror of the merge-side rule: a web-only merge needs only the rebuild, *since the build is served from disk per request*. One fact read from opposite sides, of which only the merge side had ever been stated where the serving step reads it. The verification is a grep of the **built** assets for a marker only your change emits, not a re-reading of the source. The cost of missing it is a reviewer shown the old build in place of the change. Every restore path in `scripts/plant.sh` prints the warning at the moment the trap arms, because reading the doc is not what saves anyone here — the grep is.
  **When a plant fails to fail, suspect the test data before the assertion.** A fixture must be representative enough to exercise the behavior under test — a terse mock `why` puts no flex-shrink pressure on a label-width assertion — and an expected value must be distinctive enough that its presence implies correctness, which a `toContain` check cannot claim against a document that quotes wrong values as counterexamples.
  **A check is designed against its nearest alternative:** before writing it, name what else would also pass it. **A fixture varies ONLY the axis the assertion keys on** — a fixture where every entity differs on every axis identifies no axis; **a claimed rate states its sample size** and cannot come from a handful of runs; **a visual result is verified by probing the property at the moment of capture, never by looking at the output.** Four shapes of this failure, all under the rules above: a fixture keyed every session to its own directory, so six passing tests could not tell grouping-by-session from grouping-by-cwd — on a real store (nine sessions, one checkout) that undetected difference collapses the whole diary into one card; a test named a NaN guard and proved nothing about it, because without the guard the comparator fell through to a tie-break producing the same order at the fixture's ids, and the fix was a discriminating fixture (id 99 — fallback puts it first, the guard puts it last) rather than a weaker test; a 5/5-green sample was read as "deterministic" against a believed ~40% rate; and two visual inspections passed screenshots carrying a real artefact, where only a probe at shutter time (`boxShadow: 2.18px` — a transition mid-flight) discriminated. The rule above governs what a fixture RETURNS; this one governs which axes it varies.
- **Position, scroll, and focus assertions are shown to fail:** every new assertion about position, scroll, focus, or anything the browser partially does on its own is hand-run with the behavior deleted — per assertion, not per change — and that run's failure output is recorded. The browser doing half the job for free is exactly how a toothless assertion ships green. Deleting your own behavior to prove an assertion is a **plant**, so it goes through `scripts/plant.sh --check` like any other; `control` mode borrows *another tree's* content, which is a different thing under a similar name.
- **Themed visual states are asserted in both themes, and style signatures per channel.** Any assertion about a visual state a theme can change runs in light *and* dark, driven through the app's own toggle — a selected-verdict styling that the outline variant's dark overrides suppressed shipped green because the scenario only ever rendered one theme. And a style-signature assertion compares each style channel on its own, never as one joined value: any single surviving channel satisfies a whole-string inequality, so the joined form passes a broken state and cannot name which property carried the difference.
- **OS-acting seams default to no-op in the harness.** Any runtime seam that touches the OS — kill, spawn, network, filesystem outside the stage — is a no-op under test by default, injectable to *enable*, never to disable. A seam that defaults live once nearly killed the test runner.
- **The mock world is stateful and typed, and both properties are load-bearing:** a module reload resets the world — never `page.reload()` after a MockControl call; and a field the world does not model must not be canned — model it or leave it to fail the type check. The mock module's own header carries the same two sentences.
- **Suite 5 runs under Node, not Bun** — Playwright spawns its own runtime, so no Bun APIs (`Bun.*`, `bun:sqlite`, `import.meta.dir`) in `e2e/`; Bun-specific work goes through helpers spawned as real Bun processes.
- **No manual browser driving, ever.** The UI is looked at only through Playwright screenshots and traces. "Just checking something" = write a scenario.
- **No ad-hoc state probes** — diagnostics go through the CLI and structured logs.
- **Never truncate a runner's summary.** A positional filter over a suite's output can crop exactly the line that carries the verdict. Extract counts only with a failure-preserving pattern — `grep -E "[0-9]+ (passed|failed|flaky)"` — and **every count in a report travels with its full summary line beside it**. A `| tail -1` that kept "29 passed" and dropped "7 failed" was about to report a live keyboard flake as not reproducible, the exact opposite of the truth; every number taken through a cropping filter had to be re-measured before it could be trusted.
- **Never suppress bddgen's output, and a passing web run proves nothing unless bddgen regenerated in the same command.** Generation failure *is* the output, so muting it converts a failed regeneration into a silent stale-green. `bddgen >/dev/null 2>&1 && playwright test` once reported 3 passed off the previous generation, because a typographic apostrophe in a step name against the feature's straight one made bddgen report "Missing step definitions" into `/dev/null` — exactly the class of difference a human eye skips.
- **Verification before any claim of doneness.** The standing check, kept as a script: headless-load every route with **zero console errors and zero pageerrors**, non-empty bodies, no byte-identical screenshots, clean worktree, claimed artifacts actually present.
